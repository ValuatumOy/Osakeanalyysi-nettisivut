# Automating report landing-page content

## What is actually manual today

The report PDF is already generated by `pdf-report-engine`. The HTML landing page is already
generated by `scripts/build-report-pages.mjs`. The only manual step between them is writing
`report-content/<id>.json` — reading the PDF and turning it into the ~23 structured fields the
build script renders. Commit 4627fbb is a typical example: one new `report-content` file, plus a
rebuild.

So the thing to automate is exactly one transform:

    reports/pdfs/<Name>_<ddmmyyyy>.pdf  ──►  report-content/<id>.json

This directory is the harness for measuring how well, and how cheaply, a model does that.

## Setup

    cp .env.example .env      # fill in OPENROUTER_API_KEY

`pdftotext` (poppler-utils) must be on PATH for the default text mode.

## Generate

Pass a catalog report id, not a local path — the generator downloads that report's PDF from the
live catalog and caches it under `scripts/report-ai/pdf-cache/`:

    npm run report:generate -- teslainc-05082026
    npm run report:generate -- --latest 3

`reports/pdfs/` is gitignored, so it is a personal snapshot that drifts: at the time of writing it
held 16 PDFs that were no longer in the catalog and was missing every report published after
24 July. Local paths still work for a one-off, but a run based on that directory is not a run
against what the site actually serves.

    npm run report:generate -- reports/pdfs/Tesla_23072026.pdf

Output lands in `scripts/report-ai/out/<id>.json` — never in `report-content/`, so a test run
cannot overwrite a hand-written file. Copy it across yourself once it is good enough.

Each run prints measured spend and appends a line to `scripts/report-ai/runs.jsonl`:

    → Tesla_23072026.pdf via anthropic/claude-sonnet-5
      $0.0000  0 in / 0 out  0.0s  → scripts/report-ai/out/tesla-23072026.json

The dollar figure is OpenRouter's own `usage.cost`, i.e. what your account was actually charged,
not an estimate from a price table.

Useful flags:

| Flag | Why |
| --- | --- |
| `--model <slug>` | The variable you are testing. Any OpenRouter model with structured-output support. |
| `--dry-run` | Prompt size and page count, no API call and no spend. |
| `--example <id>` | Few-shot with a hand-written file, e.g. `--example nokia-15072026`. Costs roughly 9k extra input tokens per run; compare quality with and without. |
| `--pdf-native` | Send the PDF instead of `pdftotext` output. `--pdf-engine mistral-ocr` costs $2/1,000 pages on top of tokens; `pdf-text` is free. |
| `--reasoning low\|medium\|high` | For reasoning models. Reasoning tokens are billed as output. |
| `--json` | Machine-readable run summary, for scripting a sweep. |

A whole sweep in one command:

    npm run report:generate -- reports/pdfs/*.pdf --model <slug> --out /tmp/sweep-<slug>

## Compare against the hand-written reports

    npm run report:compare -- scripts/report-ai/out/tesla-23072026.json

The generated file is paired with the `report-content/` file for the same ticker and report date.
Three verdicts, because they fail for different reasons:

- **Structure** — everything `build-report-pages.mjs` reads is present, financial rows have one
  value per column, and Bull/Base/Bear all exist. A structural failure breaks the page build.
- **Facts** — every rating, price, multiple, financial-table cell, scenario cell and value-pool
  share is compared to the hand-written file, with separators and `×`/`x` normalised away. This is
  the number that matters: published figures have to be exact.
- **Shape** — section counts and average words per section, against the reference.

A fourth line, **style**, counts mechanical prose defects that an LLM judge reliably penalises:
a figure with no currency or scale (`revenue of 479,971`), narrating the source document ("the
report describes…"), restating the scenario table in prose, justifying the rating with the
arithmetic that produced it, and padding a value pool the report does not value. The hand-written
files score 0; the first version of this prompt scored 19-23. It runs locally and free, so prompt
changes can be iterated without paying for a judgement each round, and the generator uses the same
check to repair its own output before writing the file (disable with `--no-repair`).

Two known false-positive sources, both left in deliberately rather than papered over: a base-case
scenario figure legitimately reappears in the target-price bridge, and a count that happens to
equal a scenario value ("450,000 paid rides") reads as a restatement. Treat a residual count of
1-2 as clean and read the excerpts before acting on them.

Add `--judge <model>` for an LLM read of prose quality against the reference (faithfulness,
analytical depth, house style, SEO usefulness, plus a publishable/needs-rework verdict). Its own
cost is printed separately so it never contaminates the generation-cost measurement.

Note that only some local PDFs have a same-date hand-written counterpart; where the dates differ
the tool says so and the factual diffs are expected rather than model errors.

## Measured so far (6 Aug 2026)

Four models over the Nvidia 16 July and Oriola 1 June reports, ~15-19k input / 5-6k output tokens each:

| Model | Cost per report | Facts | Notes |
| --- | --- | --- | --- |
| `openai/gpt-5.6-luna` | $0.005 | 214/216 | Best value; the two misses are a rounding tie, not errors |
| `openai/gpt-5.6-terra` | $0.052 | 214/216 | Same accuracy, slightly stronger prose, 10x the cost |
| `~deepseek/deepseek-v4-flash-latest` | $0.006 | 185/186 | Two of three attempts hit the 15-minute timeout; unusable as-is |
| `~google/gemini-flash-latest` | $0.095 | 185/186 | Weakest prose and the highest cost; heavy reasoning-token spend |

Fact extraction is not the hard part — every model reproduces the numbers. On the current Tesla
report (5 August, 33 pages) gpt-5.6-luna scores 152/152. Prose quality and reliability are what
separate the models.

Prose, judged five times per model against the reference (Claude Opus 5, Nvidia report). The
house-style rules below were tuned between the two rounds:

| | faithfulness | depth | house style | SEO |
| --- | --- | --- | --- | --- |
| `gpt-5.6-terra`, first prompt | 4.0 | 3.0 | 4.0 | 4.0 |
| `gpt-5.6-luna`, first prompt | 3.8 | 3.0 | 3.2 | 4.0 |
| `gpt-5.6-terra`, current prompt | 4.0 | 4.0 | 3.8 | 4.0 |
| `gpt-5.6-luna`, current prompt | 4.0 | 4.0 | 4.0 | 4.0 |

The gap closed: luna started 0.25 points behind on average and now matches terra, at a tenth of
the cost. On the 5 August Tesla report — which was never used while tuning the prompt — luna
scored 4.0/4.0/4.0/4.0 against terra's 3.3/4.0/4.0/4.0 over three samples each. Every sample from
both models still lands on *publishable-after-light-edit*; neither reaches publish-as-is.

What moved the numbers was not more prose instruction but naming the specific mechanical defects
and letting the tooling check them. (That checker, `scripts/report-pages/style.mjs`, was later
removed — see `docs/report-page-automation.md` — after its `unitless-figure` and
`scenario-recitation` rules started producing unfixable false positives on real reports; this
section's numbers still describe why it was built.)

Two findings worth keeping in mind when reading a low score:

- **The hand-written reference is not always right.** It abbreviates `NASDAQ Global Select` to
  `NASDAQ`, takes value-pool shares from the chart labels (`27%`) where the models take the more
  precise table figure (`26.7%`), and omits the balance-sheet table from the Nvidia report
  entirely. Check the PDF before treating a mismatch as a model error.
- **The `pdftotext` layer renders some decimal points as spaces** — `-0 9×` means -0.9x. This
  appears in 11 of the 17 local PDFs, always on the Net debt / EBITDA row. The prompt now tells
  the model to restore the decimal point; if a new row starts showing this, widen that rule.

## Reading the results

Per-report generation cost is the headline number, but the decision also depends on:

- **Fact accuracy.** Below ~100% on headline and financial-table fields, a human has to check every
  figure anyway, and most of the manual effort survives.
- **Retry cost.** A cheap model that needs two attempts is not cheap.
- **Where the errors are.** A wrong price target is fatal; a value pool ordered differently is not.

## The subscription alternative

`scripts/company-pages/profile-provider.mjs` already shells out to a subscription CLI (`codex
exec`) for company profiles, so the same shape works here: swap the OpenRouter call for a
`claude -p` (or `codex exec`) invocation with the same prompt and schema. Keep this harness either
way — it is how you would confirm the subscription route produces output as good as the per-token
route before switching.
